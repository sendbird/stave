# Internationalization (i18n)

Stave's own UI ships in **English** (default, source language) and **Korean**.
Every user-facing string exists in both languages, and the build fails when one
is missing. Users switch languages in **Settings → General → Language**; the
choice persists and also drives native menus and dialogs in the Electron main
process.

The stack is [i18next](https://www.i18next.com/) with
[react-i18next](https://react.i18next.com/). Catalogs are bundled JSON, so the
app works offline and never shows a raw key.

## Layout

| Path | Purpose |
| --- | --- |
| `src/locales/en/<namespace>.json` | English source catalog. Defines the key set and the TypeScript key types. |
| `src/locales/ko/<namespace>.json` | Korean catalog. Must mirror English (plural forms excepted). |
| `src/i18n/runtime.ts` | React-free synchronous instance for shared renderer/main/preload helpers. |
| `src/i18n/index.ts` | Renderer instance, `useTranslation`, `Trans`, `applyAppLocale`, `I18nKey`. |
| `src/i18n/resources.ts` | Namespace registry. Every catalog file must be imported here. |
| `src/i18n/format.ts` | Locale-aware date, time, number, list and relative-time formatting. |
| `src/i18n/locale.ts` | `AppLocale` contract shared with the store and the main process. |
| `electron/main/i18n.ts` | Main-process instance (`desktop` and `common` namespaces) and locale persistence. |
| `config/i18n.json` | Gate configuration: scan scope, allowlisted terms, untranslated-key exceptions. |
| `scripts/check-i18n.mjs` | The gate (`bun run check:i18n`). |

### Namespaces

One namespace per feature area. Pick the namespace of the feature that owns the
screen, not the component's directory.

| Namespace | Covers |
| --- | --- |
| `common` | Shared verbs, statuses and generic labels (`actions.save`, `status.running`). Add only text that means the same thing everywhere. |
| `desktop` | Electron main-process menus and native dialogs. |
| `settings` | Settings dialog shell, search registry, and general/app sections. |
| `settingsProviders` | Provider, model, MCP and tooling settings. |
| `settingsConnections` | Auto routing, secrets, API connections, provider accounts and connectors. |
| `shell` | App shell, top bar, status bar, sidebar navigation, command palette, shortcuts. |
| `editor` | Editor panel and file views. |
| `terminal` | Terminal and CLI session surfaces. |
| `workspace` | Workspace sidebar, information panel, resources, memory, create/continue/cleanup flows. |
| `automation` | Automation center, schedules and check-backs. |
| `kickoff` | Kickoff and dispatch flows. |
| `issues` | Tracker issues. |
| `fleet` | Fleet view and attention inbox. |
| `sourceControl` | Branches, changes, pull requests and source-control reviews. |
| `gitGraph` | Git graph. |
| `session` | Chat area, task panel, turn activity. |
| `composer` | Prompt input, composer shelf and message rendering. |
| `panes` | Workspace panes. |
| `lens` | Lens surfaces. |
| `scripts` | Workspace tools and scripts. |
| `agents` | Agent library and editor. |
| `agentRuns` | Agent runs, workflows, delegation and supervision. |
| `providers` | Provider runtime options, models and command catalogs. |
| `usage` | Usage and quota views. |
| `compare` | Compare runs and results. |
| `ui` | Shared UI and ADS component defaults. |
| `notifications` | Toasts and notifications raised from store actions. |
| `app` | App-level text that belongs to no feature above. |

To add a namespace: create `src/locales/en/<ns>.json` and
`src/locales/ko/<ns>.json`, register both in `src/i18n/resources.ts` (import,
`I18N_NAMESPACES`, `sourceResources`, `resources.ko`), add a row above, and run
`bun run check:i18n`.

## Writing code

```tsx
import { useTranslation } from "@/i18n";

export function TaskListEmpty({ count }: { count: number }) {
  const { t } = useTranslation(["session", "common"]);
  return (
    <section aria-label={t("taskList.ariaLabel")}>
      <p>{t("taskList.empty.title")}</p>
      <p>{t("taskList.summary", { count })}</p>
      <button type="button">{t("common:actions.retry")}</button>
    </section>
  );
}
```

Rules:

1. **Import from `@/i18n`, never from `react-i18next` or `i18next` directly.**
   The module initializes the instance before anything renders or runs.
   Shared non-component modules also imported by main or preload use
   `src/i18n/runtime.ts`, which exports the same instance without importing React.
   Keep model-facing prompts and protocol metadata independent of this instance.
2. **Components that render translated text call `useTranslation()`.** That
   subscription is what re-renders them when the language changes; reading
   `i18n.t` during render alone does not.
   Add the locale to memo dependencies only when the memo computes translated
   presentation. Do not invalidate provider options, terminal controllers or
   session objects on a language change; it must not reconnect a live session.
   Accessible names are human copy, including names that used to look like
   `open-settings`. Put stable automation identities in `data-testid`.
3. **Never call `t` at module scope.** Module constants are evaluated once, in
   whatever language was active at import time. Keep keys in tables and
   translate where the text is rendered:

   ```ts
   import type { I18nKey } from "@/i18n";

   export const STATUS_LABEL_KEYS = {
     running: "common:status.running",
     done: "common:status.completed",
   } as const satisfies Record<string, I18nKey>;

   // In the component: t(STATUS_LABEL_KEYS[status])
   ```

   Helpers that build text accept `t: AppTFunction` (or a specific `TFunction`)
   as a parameter, or call `i18n.t("ns:key")` when they run at event time (for
   example while raising a toast).
4. **Outside React**, use `i18n.t("namespace:key", options)` from `@/i18n`.
5. **No string concatenation.** Translate whole sentences with interpolation:
   `t("branch.deleted", { name })` → `"Deleted {{name}}"` /
   `"{{name}} 브랜치를 삭제했습니다"`. Word order differs between languages.
6. **Plurals** use `count` and i18next suffixes. English needs `_one` and
   `_other`; Korean has no plural distinction and uses only `_other`:

   ```json
   // en
   { "files_one": "{{count}} file", "files_other": "{{count}} files" }
   // ko
   { "files_other": "파일 {{count}}개" }
   ```

7. **Markup inside a sentence** uses `<Trans>` with named tags, not split keys:

   ```tsx
   <Trans t={t} i18nKey="composer.hint" components={{ kbd: <kbd /> }} />
   // en: "Press <kbd>Enter</kbd> to send"  ko: "<kbd>Enter</kbd> 키를 눌러 보내기"
   ```

8. **Dates, times, numbers and relative times** use the helpers in `src/i18n/format.ts`
   (`formatDateTime`, `formatRelativeTime`, `formatNumber`, `formatList`, …).
   Do not call `toLocaleString()` without a locale or hardcode `"en-US"`.
9. **Errors shown to users** get a translated summary. A raw technical detail
   (`error.message`, stderr) may follow it untranslated:
   `t("common:errors.withDetail", { detail: error.message })`.
10. **Accessibility text is UI text.** `aria-label`, `title`, `alt` and
    placeholder values are translated like visible copy.

### Keys

- Segments are `lowerCamelCase`, nested by surface and element:
  `settings:general.language.title`, `session:taskList.empty.title`.
- Name keys by meaning, not by their English wording. Rewording the English
  text must not require renaming the key.
- Do not reuse one key for two meanings just because the English matches
  ("Open" a file vs. "Open" status). Shared meanings belong in `common`.
- Delete keys you stop using in the same change.

### What is not translated

- User content: prompts, file contents, task titles the user typed, notes.
- Provider and AI output, tool output, terminal output.
- Text sent to models: system prompts, tool descriptions, MCP tool schemas.
  AI response language is a separate concern from the display language.
- Protocol values, ids, setting keys, CSS, test ids, keyboard accelerators.
- Log, console and diagnostic error messages that are not shown as UI copy.
- Product and service names (`Stave`, `Claude`, `Codex`, `GitHub`, …), which
  are listed in `config/i18n.json` → `terms`.

When the gate flags such a literal, mark it on the same line or on a comment
line directly above:

```ts
// i18n-ignore: model-facing tool description
const description = "List the files in the workspace.";
```

The reason after the colon is required by review, not by the tool; keep it
specific.

### Persisted text

Text that is stored (notification history, generated task titles) keeps the
language that was active when it was created. Prefer storing a key and its
parameters for anything that must re-render in the current language.

## The gate

`bun run check:i18n` runs in `test:ci`, `build` and `build:desktop`. It fails
when:

- a namespace exists for one locale but not the other, or is not registered in
  `src/i18n/resources.ts`;
- a catalog is not canonical JSON (fix with `bun run check:i18n --fix`);
- a key is missing, empty or extra in a locale; interpolation variables or
  `<Trans>` tags differ; a locale lacks a plural form its language needs or has
  one it never uses;
- a Korean value contains no Korean text although the English value has words
  to translate (acronyms and `terms` are exempt; add a deliberate exception to
  `untranslatedKeys` as `namespace:key`);
- a key segment is not `lowerCamelCase`;
- a user-facing string literal remains in renderer code or in the main-process
  files listed in `config/i18n.json` (JSX text, user-facing attributes and
  props, `toast(...)`, copy tables and label helpers).

Useful modes:

```sh
bun run check:i18n                       # full gate
bun run check:i18n --catalogs            # catalogs only
bun run check:i18n --files <file>...     # scan specific files
bun run check:i18n --summary             # hardcoded strings per file
```

TypeScript checks keys: `t("missing.key")` is a type error because the English
catalogs define the key types (`src/i18n/i18next.d.ts`).

## Tests

Tests run in English, so existing English assertions keep working once text
moves into catalogs. To assert Korean, call `applyAppLocale("ko")` and reset
with `applyAppLocale("en")` in `afterEach`.

## Korean style guide

- **Sentences** (descriptions, empty states, errors, confirmations) use the
  formal declarative `합니다` style: `설정을 저장했습니다.`,
  `파일을 불러오지 못했습니다.`
- **Questions** use `하시겠습니까?`: `이 워크스페이스를 삭제하시겠습니까?`
- **Buttons, menu items, tabs and field labels** are short noun phrases without
  a sentence ending: `저장`, `다시 시도`, `새 워크스페이스`, `브랜치 삭제`.
- **Placeholders** are short noun phrases or `~ 입력` / `~ 검색`:
  `작업 검색…`, `브랜치 이름 입력`.
- **Status words** use the `~됨` / `~ 중` forms: `완료됨`, `실행 중`, `일시 중지됨`.
- Do not use `당신`. Address the reader implicitly.
- Keep product names, code, commands, file paths, key names and acronyms
  (`PR`, `MCP`, `CLI`, `API`, `URL`) as written in English.
- Particles after a variable depend on its final sound (`을/를`, `이/가`,
  `은/는`, `으로/로`). Put a noun between the variable and the particle
  (`{{name}} 브랜치를`) or rephrase so no particle follows the variable.
- Counters follow the number: `파일 {{count}}개`, `{{count}}분 전`.
- Keep the ellipsis character `…` where English uses it.
